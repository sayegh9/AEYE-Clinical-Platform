# AEYE Clinical Platform Architecture

This document defines the deterministic, agentic workflow that powers AEYE — a refractive surgery and ectasia-risk decision support system designed for deployment in a Dify-style advanced-chat experience. All logic below is aligned with AAO and ESCRS guidance, Belin–Ambrósio Enhanced Ectasia Display (BAD-D) rules, and the safety constraints in the product specification.

## 1. System Overview

AEYE executes as a multi-node conversational workflow. Each node is either an LLM agent (with schema-enforced JSON output) or a deterministic Python/code node. Nodes write to scoped conversation variables that serve as structured memory, ensuring idempotent behavior and repeatability.

### Entry Inputs
- **documents**: Referral letters, OPD sheets, surgical planning forms, etc.
- **images**: Pentacam/Scheimpflug tomography, AS-OCT, and other anterior segment imaging.
- **sys.query**: User’s typed instruction or question.

### Core Conversation Variables (Global State)
| Variable | Description |
| --- | --- |
| `patient_history` | Structured demographics, history, refraction, and contact-lens profile captured by the General Ophthalmology Agent. |
| `pentacam_processed_data` | Raw per-scan metrics (per eye) output by the Pentacam & AS-OCT Agent. |
| `imaging_data_stored` | Aggregated, canonical per-eye dataset produced by the merge code node. |
| `interpretation_report` | Full tomography interpretation from the Pentacam Interpretation Agent. |
| `pta_rsb_table` | Deterministic PTA/RSB values for each eye × modality, generated by the PTA & RSB Calculator. |
| `diagnosis_and_plan` | Final structured assessment from the Anterior Segment Specialist Agent. |
| `assessment_complete` | String/boolean flag used for routing follow-up queries. |

All variables share fixed JSON schemas, maintained by validator snippets inside each node prompt/code block. Empty or missing fields are represented by empty strings (`""`) or omitted keys—not placeholders.

## 2. Workflow Topology

```
Start → Orchestrator Agent → Validate Intent (code) → Route by validated_intent
```

- **INITIAL_ASSESSMENT path**
  1. Doc Extractor → Merge Text (code) → General Ophthalmology Agent → `patient_history`.
  2. Imaging loop: Pentacam & AS-OCT Agent (per file) → `pentacam_processed_data` → Aggregate Pentacam Data (code) → `imaging_data_stored`.
  3. Pentacam Interpretation Agent → `interpretation_report`.
  4. PTA & RSB Calculator (code) → `pta_rsb_table`.
  5. Anterior Segment Specialist Agent (Initial Mode) → `diagnosis_and_plan`.
  6. Set `assessment_complete = "True"` → Final Report Formatter (code) → Answer node (Markdown report).

- **FOLLOW_UP_QUERY path**
  - Skip extraction agents. Anterior Segment Specialist Agent (Follow-Up Mode) consumes stored variables and produces a concise chart note answering the query.

- **UNHANDLED_QUERY**
  - Answer node responds with a clarification request, prompting the clinician to upload data or specify relation to an existing AEYE report.

## 3. Node Specifications

### 3.1 Orchestrator Agent (Intent Router)
- **Model**: GPT-4o-mini (or equivalent compact routing model).
- **Output schema**: `{ "intent": "INITIAL_ASSESSMENT" | "FOLLOW_UP_QUERY" | "UNHANDLED_QUERY", "rationale": "..." }`.
- **Rules**:
  - First turn + files → `INITIAL_ASSESSMENT`.
  - New files mid-session → `INITIAL_ASSESSMENT`.
  - `assessment_complete == true` + no new files → `FOLLOW_UP_QUERY`.
  - Text containing “analyze/review patient/assessment” without prior report → `INITIAL_ASSESSMENT`.
  - Otherwise → `UNHANDLED_QUERY`.

### 3.2 Validate Orchestrator Output (Code Node)
- Deterministically recomputes `validated_intent` using the same priority stack:
  1. Presence of new files or first-turn files.
  2. `assessment_complete` true with zero new files → `FOLLOW_UP_QUERY`.
  3. Textual triggers for initial assessment.
  4. Fallback to `UNHANDLED_QUERY`.
- Overrides the LLM decision when mismatched to guarantee deterministic routing.

### 3.3 General Ophthalmology Agent (History Collector)
- **Input**: `combined_patient_text`.
- **Output**: Structured `patient_history` object containing demographics, systemic/ocular history, refraction, IOP, and contact-lens profile (including washout computation). Key logic:
  - Compute `days_since_last_wear` and compare to modality-specific washout thresholds:
    | Lens Type | Tomography | Refraction | ETM |
    | --- | --- | --- | --- |
    | Soft/unspecified | 7 d | 14 d | 14 d |
    | RGP | 21 d | 28 d | 28 d |
    | Scleral | 28 d | 28 d | 28 d |
    | Ortho-K | 28 d | 42 d | 42 d |
  - Add policy strings to `clinical_notes_or_tags` and `management_notes` summarizing washout sufficiency.
  - `final_impression` summarises history-based risk (e.g., “High ectasia risk due to FHx keratoconus and chronic rubbing”).

### 3.4 Pentacam & AS-OCT Agent (Raw Imaging Processor)
- Executes inside a file iteration node; each run returns per-eye structures with fields for keratometry, pachymetry, elevation, BAD-D, ART-Max, pattern descriptors, heatmap summaries, and scan quality remarks. Outputs append to `pentacam_processed_data` (list keyed by scan ID).

### 3.5 Aggregate Pentacam Data (Code Node)
- Consolidates multiple scans into `imaging_data_stored`:
  - Aligns eyes via labels + metadata; flags OD/OS mismatches.
  - Chooses best-quality scan per eye (priority: repeatability confirmed > higher image quality > latest timestamp).
  - Extracts canonical numeric metrics: `k1`, `k2`, `kmax`, `thinnest_pachymetry`, `posterior_elevation_at_thinnest`, `art_max`, `isv`, `ihd`, `iva`, `iha`, `q_value_6mm`, `rmin`, `progression_index`, pattern descriptors, and quality flags.
  - Stores scan provenance for traceability.

### 3.6 Pentacam Interpretation Agent
- Consumes `patient_history`, `imaging_data_stored`, and raw scans.
- Produces `interpretation_report` featuring:
  - `interpretation_summary` with patient/date metadata.
  - `eye_interpretations` array, each containing raw metrics, pachymetry/elevation analysis, BAD-D interpretation, parameter flags, risk level, scan consistency checks, classification tags, diagnostic impression, and recommendations.
  - `global_considerations` (inter-ocular asymmetry, bilateral risk assessment, progression evaluation, CXL indications, surgical suitability).
  - `quality_control` (repeatability, contact-lens washout status, metric repeatability deltas).
  - `guideline_checks` booleans confirming ESCRS/AAO adherence.

### 3.7 PTA & RSB Calculator (Code Node)
- For each eye and modality, compute ablation depth using Munnerlyn approximation:
  ```
  ablation_depth = (|intended_correction_D| * optical_zone_mm^2) / 3
  ```
- Use modality-specific flap/cap thickness assumptions (110 µm Femto-LASIK, 120 µm LASIK/SMILE cap, 0 µm PRK/Trans-PRK).
- Calculate:
  - `PTA = (flap_or_cap + ablation_depth) / CCT`.
  - `RSB = CCT − (flap_or_cap + ablation_depth)`.
- Store deterministic results under `pta_rsb_table[eye][modality] = { "pta": float, "rsb_um": float, "assumptions": [ ... ] }`.
- If refraction missing, record `assumptions` noting placeholder corrections and mark outputs as provisional (no eligibility decisions based solely on provisional PTA/RSB).

### 3.8 Anterior Segment Specialist Agent – Initial Mode
- Integrates all prior variables to produce `diagnosis_and_plan` with sections:
  - `mandatory_imaging_data` per eye (BAD-D, ART-Max, pachymetry, posterior elevation, keratometry, indices, heatmap patterns, quality flags).
  - `chief_complaint_resolution` and `imaging_summary`.
  - `corneal_tomography_interpretation` (per-eye narrative referencing BAD-D thresholds, ART-Max, posterior elevation, ABCD staging, CTSP, etc.).
  - `pta_rsb_table` replication and commentary.
  - `modality_eligibility` entries for LASIK, Femto-LASIK, PRK, Trans-PRK, SMILE, ICL, CXL, ICRS/CAIRS, keratoplasty with `{status, rationale, triggers[]}`.
  - `eligibility_justifications` tying each procedure to explicit metrics and guideline thresholds.
  - `final_recommendation`, `next_steps`, `critical_flags`, optional follow-up tables, and references.
- **Ectasia Risk Overrides** (hard-coded in prompt and guarded by code comments):
  - BAD-D ≥ 2.6, `bad_d_category = Abnormal`, ART-Max < 300 µm, posterior elevation ≥ 20 µm in ectatic pattern, or classic ectatic heatmaps → lamellar procedures (LASIK/Femto-LASIK/SMILE) automatically `contraindicated` regardless of PTA/RSB.
  - ≥2 suspect triggers (e.g., BAD-D 1.6–2.6 plus ART-Max 320 µm) restrict lamellar surgeries to `caution` at best.
  - CL washout incomplete/unknown → lamellar modalities downgraded to `defer` and flagged in `quality_flags`.
  - Poor repeatability or missing core indices → output “Case inconclusive — repeat tomography.”

### 3.9 Anterior Segment Specialist Agent – Follow-Up Mode
- Activated when `validated_intent = FOLLOW_UP_QUERY`.
- Reads stored variables only; does **not** re-run extraction.
- Response style: concise chart note with 2–5 sentences covering metric deltas, risk trajectory, recommendation, and next test/interval. Upholds prior contraindications unless new validated data exists.

### 3.10 Report Formatter (Code Node)
- Converts `diagnosis_and_plan` into a clinician-facing Markdown summary:
  - TL;DR with chief risks.
  - Structured sections (History, Imaging Snapshot, Ectasia Risk, Procedure Eligibility, Recommendation, Follow-Up Steps).
  - Appendices referencing metrics, PTA/RSB tables, and quality notes.
- Ensures idempotent formatting and deterministic ordering of sections/eyes.

## 4. Safety & Determinism

1. **Intent validation**: Code node enforces routing; no clinical output without validated intent.
2. **Data integrity**: Aggregation node rejects eye swaps, duplicates, or conflicting scans (prompts rerun).
3. **Hard limits**:
   - `RSB < 300 µm` → lamellar contraindicated.
   - `PTA > 0.40` (LASIK/Femto-LASIK) or `PTA > 0.38` (SMILE) → contraindicated.
   - Ectasia pattern overrides PTA/RSB (per Section 3.8).
4. **CL washout gate**: If thresholds unmet, lamellar modalities cannot be labeled “eligible.”
5. **Quality control**: Missing BAD-D, ART-Max, thinnest pachymetry, or posterior elevation prevents positive eligibility; output instructs user to obtain adequate data.
6. **Idempotence**: Code nodes and schema validations ensure identical inputs yield identical outputs; prompts avoid stochastic phrasing and rely on deterministic pattern templates.

## 5. Initial vs Follow-Up Experience

| Phase | Behavior |
| --- | --- |
| Initial Assessment | Full pipeline runs; outputs include structured Markdown report and stored conversation state. |
| Follow-Up Query | Uses stored state to generate delta-focused chart notes; no re-ingestion unless new files appear. |
| Unhandled Query | AEYE requests clarification or data upload, avoiding hallucinated clinical decisions. |

## 6. Report Structure (Clinician-Facing)

1. **Header**: Patient demographics, visit date/time, reason for consult.
2. **History Snapshot**: Key systemic/ocular factors, refraction, contact-lens washout status.
3. **Imaging Snapshot**: Table listing OD/OS metrics (BAD-D, ART-Max, Kmax, thinnest pachymetry, posterior elevation, quality flags).
4. **Risk Assessment**: Narrative integrating tomography patterns, BAD-D categories, ART-Max, posterior elevation, and CL washout context.
5. **PTA & RSB Table**: Per eye × modality with numeric PTA/RSB, thresholds, and color-coded status (OK/Caution/Unsafe).
6. **Procedure Eligibility**: Bullet list summarizing lamellar vs surface vs additive procedures, with explicit triggers causing contraindications.
7. **Plan & Follow-Up**: Final recommendation, next steps (repeat imaging intervals, biomechanics, ETM), and guideline references.
8. **Appendix**: Structured JSON (if needed) for EMR integration.

## 7. Extensibility Hooks

- **Epithelial Thickness Map (ETM) Agent**: Reserve `conversation.etm_data` for future modules. Aggregation and interpretation prompts already reference this field, enabling plug-in without schema changes.
- **Progression Tracker**: `diagnosis_and_plan` includes optional `followup_plan_table` and `references_evidence_base`; these accommodate time-series deltas and alerts once prior reports are ingested.

## 8. Deployment & Reproducibility

- Store this workflow as a Dify advanced-chat template (JSON/YAML) with explicit node wiring per sections above.
- Version control prompts and code snippets to maintain clinical traceability.
- Default models: GPT-4o-mini for routing/lightweight nodes; GPT-4o (or equivalent) for interpretation and specialist agents.
- Code nodes run on Python 3.11+ with deterministic libraries only (no network calls, no randomness).

By adhering to this architecture, AEYE reliably delivers clinically conservative, guideline-aligned refractive surgery eligibility assessments while maintaining strict safety, auditability, and extensibility.
